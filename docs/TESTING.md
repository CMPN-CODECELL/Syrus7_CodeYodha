# Testing and proof

## 1. Automated tests (pytest + Hypothesis)
Run: `cd backend && uv run pytest -q` (needs the Postgres and Valkey containers). Tests use an isolated database (`countersign_test`) and Valkey db 1, and plug a fault-injecting fake broker into the **real** executor pipeline. Run one suite at a time: two runs against `countersign_test` at once deadlock. No test talks to the real 021 sandbox and no fixture holds a credential: the 021 tests replay recorded sandbox responses (account code replaced by `HACK0000`, no tokens) through a scripted fake 021 server.

## 2. Formal model (TLA+ / TLC)
`formal/Countersign.tla` models approvals, tampering, replayed execution requests, the single-use capability, broker acceptance with lost responses, executor crashes and recovery.

```
cd formal
java -cp tla2tools.jar tlc2.TLC -config Countersign.cfg -deadlock Countersign.tla       # Countersign protocol
java -cp tla2tools.jar tlc2.TLC -config CountersignNaive.cfg -deadlock Countersign.tla  # naive blind retry
```
| Model | Result |
|---|---|
| Countersign (`NAIVE = FALSE`) | **No error.** 5,773 states generated, 1,521 distinct, depth 11. Invariants `NoUnapprovedOrder`, `SignedVersionOnly`, `AtMostOnce`, `TypeOK` hold in every reachable state. |
| Naive copilot (`NAIVE = TRUE`) | **`AtMostOnce` violated** in 6 steps: approve -> execute -> broker accepts but response lost -> blind retry -> second send -> two orders for one approval. |

## 4. Fault injection and chaos
* Paper broker faults (`POST /api/demo/broker-fault`): `accept_then_drop`, `delay_ack`, `reject`, `partial_fill`, `connection_failure`. On the 021 account (`CS_021_TEST_FAULTS=true`): `connection_failure` (fails in the gateway before anything is sent) and `accept_then_drop` (021 accepts, the gateway drops the answer).
* The 021 sandbox injects its own rate limits, 500/503 and timeouts at random; they cannot be switched on at will, which is why the gateway tests replay them from fixtures.
* Feed scenarios (`POST /api/demo/feed`): `dip_to_trigger` (505 -> 500 -> 499 on ABCCORP), `spike` (+3%), `crash`, `stale`, `calm`.
* Process chaos: kill the executor (`scripts/stop.py` or Task Manager) mid-plan and start it again; DBOS recovers the workflow and the outbox + reconciliation prevent duplicates.
* Toxiproxy (optional, free): `docker compose --profile chaos up -d toxiproxy`, create a proxy `127.0.0.1:18100 -> broker:8100`, set `CS_BROKER_URL=http://127.0.0.1:18100` for the executor and add a `timeout` toxic.

## 5. End-to-end smoke test
`uv run --project backend python scripts/smoke.py`: automation sign-in to the demo account (`/api/auth/demo-login`, scripts only), read-only queries, chat-drafted order, PIN countersign, executor, broker fill, outcomes, monitor (0 violations), audit chain verification.

## 6. Browser end-to-end test (real backend)
`python scripts/e2e_browser.py [--headed] [--device "Pixel 7"] [--base URL] [--broker 021 --login-file FILE]` (needs `pip install playwright httpx` and `playwright install chromium` once). Drives Chromium against the running stack the way a new trader meets Countersign, with passkeys from Chrome's WebAuthn virtual authenticator (CDP). `--device` takes any Playwright device descriptor ("Pixel 7", "iPhone 15") and runs it in Chromium.
1. **Landing page** renders with live public status; **Explore the Countersign Copilot** while signed out goes to `/signin?next=/copilot`.
2. **Sign up** a throwaway account (`e2e.<random>@example.test`); the response carries a new `PT` paper account.
3. **Onboarding**: `1234` is refused in the page and by the API (`422 WEAK_PIN`), a random strong PIN is saved, the passkey is registered, the authenticator app is linked with a computed TOTP code.
4. **Copilot**: the header is one row with three controls and "All systems normal"; *What is my P&L today?* is answered; then, with the composer switched to the **Deterministic** engine so the journey never depends on a hosted model, *Buy 10 RELIANCE* at a limit just above the live price is countersigned with the **passkey** and *Buy 1 TCS* with the **chosen PIN**, each until "Broker acknowledged" (prices come from the live quote, so the journey works on the replay feed and on live 021 prices).
5. **Attack Lab** from the UI: 9/9 BLOCKED, 0 unapproved. **Security Center**: the account panel shows the email and paper account; the kill switch is engaged (red banner) and released with the chosen PIN.
6. **Sign out**, **sign in with email and password** (then the landing page's Explore goes straight to `/copilot`), sign out, **sign in with the passkey** (no email typed), sign out, and a signed-out visit to `/copilot` redirects to `/signin?next=%2Fcopilot`.
7. **API checks** with a second new user: its paper account is seeded exactly like the demo portfolio, and it cannot list, open or approve the first user's proposals, sees no orders and gets 404 for the first user's conversation (skipped, not failed, if the first user drafted nothing). Finally, `demo-login` through the web server must answer `403`.

**`--broker 021`** runs a second journey as an existing user linked to the 021 sandbox account (email, password and PIN read from `--login-file`, never printed): sign in with the password and land on the 021 account with the gateway connected; the L1 questions (P&L, average price for INFY, NIFTY options near the money) answered from the live account; the official *If Reliance drops below 2800, buy 10*, which is already true at real prices, must produce the question with both options instead of an armed instruction; then a 1-share ITC limit order about 8% below the market is countersigned with the PIN, found in 021's order book at exactly the signed price, and cancelled through the copilot with a second PIN countersignature. The sandbox can fill an order before the cancellation arrives (it has filled limit orders far from the market); the check reports which happened instead of hiding it.

It fails on any page error and on any API response of 400 or above except the expected ones (the signed-out `401`s; a `404` from `/api/broker/*` on a backend without the gateway endpoints; the deliberate weak-PIN probe is sent outside the page). It revokes the test passkey afterwards and saves screenshots to `.logs/e2e/<device>_*.png`.

**Recorded result (2026-10-09, integration build, stack running with the 021 gateway):** paper journey 27/27 at desktop on `http://localhost:3000` and 27/27 with `--device "Pixel 7"` on the HTTPS tunnel (a first Pixel 7 run there timed out once on the passkey sign-in click and passed on the rerun); `--broker 021` 11/11 on both `http://localhost:3000` and the HTTPS tunnel, each placing a 1-share ITC limit order that appeared in 021's order book at exactly the signed price and was cancelled with a PIN countersignature (021 later reported all three as executed, the late fill after cancel described in `LIMITATIONS.md`). In the same session `scripts/smoke.py` and `scripts/flows.py` passed (0 monitor violations, audit chain intact), and `pnpm exec next typegen`, `pnpm typecheck`, `pnpm lint` and `pnpm build` were clean. A review rerun at 15:04 IST gave 26/27 at desktop: the Attack Lab check failed because scenario D's simulated spike was replaced by a live INFY tick (see `ATTACK_LAB.md`). After the fix, the desktop journey on `http://localhost:3000` passed 27/27 again (15:28 IST).
