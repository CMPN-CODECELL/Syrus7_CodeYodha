# Limitations and trade-offs (honest list)

1. **021 integration is an adapter, not live.** 021 Trade has no public API documentation, so the hackathon build runs on a fault-injecting paper broker behind the same `BrokerProvider` interface. Plugging in the real 021 APIs means implementing `ReadGateway` / `OrderExecutionProvider` against them; nothing else changes.
2. **Effectively once, not exactly once.** Delivery is at-least-once with idempotent tags and reconcile-before-retry. If the broker were to accept an order and also hide it from its own order book beyond the reconcile window, a single safe retry could duplicate it; the monitor would detect the duplicate tag and halt. Real brokers (for example Kite) do not deduplicate tags either.
3. **Simulated market.** Prices come from a deterministic replay with simple Black-Scholes option pricing, so demos never depend on live markets (NSE is closed on Saturday). Charges and margin are estimates from published schedules, labelled as estimates.
4. **Local accounts, no email.** Anyone who opens the app can sign up with a name, email and password, and gets their own paper trading account. Because everything runs locally with no mail server:
    - Emails are never verified; the email is only a unique sign-in name.
    - There is no "forgot password" email. A forgotten PIN can be reset with the account password plus the authenticator code or passkey when the trader has one (Security Center), but a forgotten password means creating a new account. For a trader whose only approval method is the PIN, the password alone can reset it, which is why onboarding and the Security Center push for a passkey.
    - There is no KYC and no self-service account deletion. Test runs (`scripts/e2e_browser.py`) leave their throwaway `e2e.*@example.test` accounts in the local database.

    Sign-in (password or passkey) is never treated as an approval.
5. **Passkey prompts do not display the order.** WebAuthn authenticators cannot show transaction details (the transaction-display extensions were never shipped by browsers), so "what you see is what you sign" depends on the approval card, which is rendered only from the canonical object whose hash is signed.
6. **PIN and TOTP fallbacks are server-attested,** not device-signed, and are labelled with lower assurance.
7. **Small local model.** `qwen3:4b-instruct` runs on a 6 GB GPU and handles tool calls, but it can be slower or less fluent than hosted models. The deterministic engine guarantees every demo flow works without any model; safety never depends on the model.
8. **Regulatory scope.** Orders sent through broker APIs are treated as algo orders under SEBI's retail algo framework (in force since 1 April 2026); Countersign enforces the 10 orders/second threshold and gives information, not investment advice. Production use would need broker empanelment, static IP whitelisting and exchange algo tagging.
9. **Same Postgres role for all processes** in local development. Production would use separate database roles with least-privilege grants per process.
10. **Toxiproxy** is provided as an optional profile; the built-in broker fault injection covers the demo scenarios.
11. **Phones are a layout target, not yet a deployment target.** The UI is responsive and was checked at iPhone 15 and Pixel 7 sizes (no horizontal overflow on any page); the full browser journey, including passkey sign-in and countersign through Chrome's virtual authenticator, passes with `--device "Pixel 7"`. The web server deliberately listens on 127.0.0.1 only (like the API and the broker), so the app cannot be opened from another device on the network at all. Serving it to phones would need, at least:
    - binding Next.js to the network address and allowing that host (`allowedDevOrigins`), which also exposes everything the proxy forwards to the API;
    - adding the address to the API's allowed origins (`CS_EXTRA_ORIGINS`).

    Passkeys on a phone also need HTTPS and a matching RP ID (for example through a free HTTPS tunnel). Over plain HTTP on a LAN, browsers disable WebAuthn, so only the PIN and authenticator-code fallbacks would work. There is no native iOS or Android app.
12. **Some controls are deployment-wide on purpose.** The kill switch, the replay feed scenarios, broker fault injection and the Attack Lab sandboxes (LAB1, NAIVE1) are shared by every account on one installation. Any signed-in trader can engage the kill switch, and any trader can release it with their own PIN. A production deployment would restrict these to an operator role. The naive copilot counter on the Attack Lab scoreboard adds up across runs (5 per full run).
13. **Rate limits and the per-client login lockout live in the API process's memory.** They reset when the API restarts and are not shared between API replicas. Per-IP limits use the TCP peer and ignore `X-Forwarded-For` (the Next.js proxy passes a browser-supplied value through unchanged), so every browser behind the local proxy shares one bucket: a busy local demo can briefly hit the sign-up (5/min) or sign-in (10/min) limits, and the per-client lockout cannot tell local browsers apart. A deployment behind a reverse proxy that sets a trusted client address header would key on that instead.
